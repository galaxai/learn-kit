Digital signatures: proving you hold a key without showing it

Goal: understand why SSH can trust a login2026-09-23style showcase

Client (your laptop) Server Private key (secret) Public key (copyable) Signature

The client wants to log in. The server must decide whether the thing on the other end really holds the private key that belongs to the account. Every idea on this page hangs off two facts you already accept.

Two truths to stand on

A public key can be copied by anyone. Possessing a copy proves nothing.

Your private key never leaves your machine. Only you can run computations with it.

If the public key proves nothing and the private key can't be sent, what can cross the wire? Something computed with the private key that can be checked without it. That object is the whole subject of this page.

The shape of the exchange

The server hands the client a fresh random challenge. The client returns a signature over it. The server checks the signature using only the copyable public key it already had.

Why random? If the challenge were fixed, an eavesdropper could replay yesterday's signature. Fresh bytes make every proof single-use.

A digital signature scheme is a pair of functions. sign(private, message) produces a signature. verify(public, message, signature) returns true or false. With a secure scheme, producing a verifying signature for a new message is infeasible without the private key.

Dependency map

Step by step, as SSH does it

  1. The client connects and both sides agree on a shared secret for encryption.
  2. The server signs a hash of the whole exchange with its host private key. The client checks it against the key remembered in known_hosts.
  3. The client signs a session-bound message with the user private key. The server checks it against authorized_keys.

Both directions are the same trick. "Server authentication" and "user authentication" are one idea, run twice with different key pairs.

Two schemes side by side

RSA

Large keys, slow to sign, fast to verify. Widely supported everywhere.

Ed25519

Small keys, fast both ways, resistant to common implementation mistakes. Preferred for new SSH keys.

In code

Conceptual sketch. The real check happens inside a library that also hashes the message first.

def prove(private_key, challenge):
    return sign(private_key, challenge)          # only the client can do this

def check(public_key, challenge, signature):
    return verify(public_key, challenge, signature)  # anyone can do this

The security condition, stated once: for a fresh message m, an attacker without the private key finds a valid signature with probability

Pr[verify(pk,m,σ)=true] ≤ε

where ε is negligible in the key size. Press ⌘ C to copy it if you like.

A signature proves possession of the private key. It does not prove the public key belongs to the person you think. Binding keys to identities is a separate problem, which is why known_hosts and authorized_keys exist.

Check yourself

The server verifies the client's signature. Which key does the server use?
  1. The client's private key
  2. The client's public key
  3. The server's private key
  4. The shared session secret

B. Verification only ever needs the public half. If the server needed the client's private key, the client would have to send it, which breaks the second truth.

Why does the server send a fresh challenge each time?
  1. To rotate the encryption key
  2. To measure round-trip latency
  3. So a recorded signature cannot be replayed
  4. To confirm the client supports the algorithm

C. A signature is tied to the exact bytes signed. New bytes, new signature. An old capture verifies against nothing.
